# Переносимые правила KMP / Compose Multiplatform

Область: изменения Kotlin Multiplatform и Compose Multiplatform. Это обычный
Markdown-контракт, подключаемый из AGENTS проекта; имя папки rules само по себе
не гарантирует автоматическую загрузку любым агентом. Продуктовые ограничения,
выбранная архитектура и явно заданная задача уточняют применение правил.

## Общий и платформенный код

- Размещать код по доступным API и потребителям source set. Не вносить прямые
  Android/JVM/Apple/Skia-импорты в commonMain. Промежуточный source set может
  использовать API, общие для всех его целей; имя папки само по себе не доказывает переносимость.
- Не прятать платформенную зависимость в общем публичном контракте. Разделять
  алгоритм и платформенный ввод/вывод через существующий механизм проекта:
  интерфейс с внедрением, expect/actual или подходящий адаптер. Не добавлять
  expect/actual и новые модули без реальной необходимости.
- Сохранять направление зависимостей проекта. Общий UI-компонент не получает
  доступ к репозиторию, DI или ViewModel ради локального действия. Импорт Compose
  в модель допустим только если это согласуется с назначением слоя, а не по умолчанию.
- Не считать успешный JVM/desktop-прогон доказательством сборки и поведения всех
  целей. Проверять затронутые настроенные targets доступными средствами;
  недоступные сборки и runtime-проверки перечислять отдельно.

## Состояние, эффекты и ресурсы

- Состояние и события публичного UI-контракта поднимать к владельцу; локальное
  состояние фокуса, раскрытия меню или редактирования хранить там, где оно принадлежит.
  Не вводить альтернативный источник бизнес-состояния внутри контрола.
- Перекомпозиция и draw не запускают бизнес-действия. Корутинные эффекты и ключи
  соответствуют времени жизни операции; ресурсы и подписки освобождаются вместе
  с владельцем. Не предполагать одинаковый lifecycle окна и Android Activity.
- Значение, которое может измениться без перезапуска жеста/эффекта, читать через
  актуальное состояние, если операция должна продолжаться. Если изменение должно
  отменить операцию, сделать это явной частью контракта ключей и отмены.
- Для динамических options хранить идентичность по стабильному значению/ключу;
  индекс использовать как позицию, не как постоянную идентичность. Явно определить
  поведение при удалении выбранного значения и отложенной загрузке данных.
- Не помечать тип Stable/Immutable только ради оптимизации. Мутабельность,
  наблюдаемость состояния и равенство должны соответствовать обещанному контракту.

## Layout, рисование и ввод

- Геометрия учитывает constraints, density, fontScale и layoutDirection. Физические
  пиксели — граница растеризации, не замена dp/sp. Не рассчитывать размеры текста
  по количеству символов и не фиксировать высоту без проверки увеличенного шрифта.
- При собственном Layout учитывать ограниченные и неограниченные оси. Не создавать
  бесконечный размер или вложенный scroll на неограниченной оси. Intrinsic measurement
  реализовывать, когда этого действительно требует поддерживаемый способ использования.
- Canvas использовать для нужной графики; стандартные механизмы текста, ввода,
  фокуса и semantics сохранять. Интерактивная Canvas-графика требует осмысленного
  доступного эквивалента; картинка с нарисованной подписью не заменяет текстовый контрол.
- Сохранять корневой Modifier вызывающего. Порядок layout/clip/draw/focus/input
  определять осознанно: внешний декор не расширяет hit area незаметно, busy/focus
  не меняют геометрию без явного требования. Области соседних действий не перекрываются.
- Учитывать способы ввода целевой платформы. Hover, touch, клавиатурный и редакторский
  фокус — разные состояния. Не навязывать desktop-правило фокуса всем платформам.
  Доступное действие имеет имя и роль; декоративная иконка не создаёт второй фокус.
- Отмена жеста/нажатия не вызывает завершённое действие. Заменять низкоуровневые
  обработчики на готовые только при сохранении семантики завершения и отмены.

## Контракт и доказательства

- Брать токены и компоненты из принятой системы проекта; не переносить палитру,
  пакетную структуру, размеры, запрет Material или формат иконок из другого приложения.
  При отсутствии решения выбрать подходящий существующий toolkit в рамках задачи.
- Изменение внешнего вида не должно незаметно менять продуктовый сценарий, порядок
  событий или сохранённые данные. Новый визуальный контракт фиксировать у его владельца.
- Проверять поведение через действия и состояние, геометрию — через измерения,
  отрисовку — через снимки/пиксели там, где это существенно. Не заменять эти проверки
  поиском строк в реализации. Для архитектурных импортов анализ исходников уместен.
- Отчёт различает сборку, тестовые взаимодействия, просмотр снимков и ручную
  проверку продукта. Подмена density/fontScale в сцене не означает изменения настроек
  ОС или системного accessibility. Пропущенные targets не объявлять проверенными.
