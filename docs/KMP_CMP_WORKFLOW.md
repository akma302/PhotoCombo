# Переносимый workflow для KMP / CMP

Набор выделен из практики проекта для повторного использования в других KMP/CMP
репозиториях. Он не задаёт продукт, визуальный стиль, архитектурные имена пакетов,
DI, версии зависимостей, Git-схему или доступные инструменты. Это переносимые тексты
правил и skills; глобальные настройки агента не изменяются.

## Состав и выбор

| Ресурс | Когда применять | Результат |
|---|---|---|
| [KMP/CMP rules](../.agents/rules/kmp-cmp.md) | Изменения общего/платформенного кода и UI | Постоянные ограничения переносимости, состояния, layout и достоверности проверки |
| [kmp-platform-change](../.agents/skills/kmp-platform-change/SKILL.md) | Перенос возможности между source sets, реализация адаптера | Корректная граница common/platform и проверки затронутых targets |
| [cmp-component](../.agents/skills/cmp-component/SKILL.md) | Создание/изменение общего UI-компонента | Контракт, компонент, пример и проверенные состояния |
| [cmp-ui-verification](../.agents/skills/cmp-ui-verification/SKILL.md) | Проверка UI-поведения, layout или визуальной регрессии | Свидетельства по вводу, геометрии и рендеру |

Rules подключаются ссылкой из AGENTS и читаются для соответствующей области.
Skills читаются по задаче; не загружать все три для обычной правки текста.
Frontmatter описывает назначение каждого skill; загрузка по имени зависит от
возможностей агента. Если автоматического обнаружения нет, использовать ссылку
на SKILL.md из точки входа проекта. Каталог rules не является универсальным форматом
автоматических инструкций для всех инструментов.

## Перенос в другой проект

Скопировать `.agents/rules/kmp-cmp.md` и нужные каталоги `.agents/skills/`, сохранив
их взаимное расположение: относительные ссылки skills ведут к общим rules.
В AGENTS нового проекта добавить ссылку на rules и маршруты только нужных skills.
Этот документ адаптации PhotoCombo копировать не требуется.

Вместо изменения универсальных файлов указать в контексте нового проекта:

- Активные модули, targets и source set hierarchy, владельца графа зависимостей.
- Источники версий и реальные команды проверки, запуска, получения артефактов.
- Выбранный UI-toolkit, дизайн-спецификацию, токены, место компонентов/примеров.
- Доступные host/SDK/backend, тестовые данные и ограничения ручной проверки.
- Продуктовые инварианты и область текущей задачи.

Не включать в общий набор имена приложения/пакетов, палитру, обязательный Canvas,
запрет Material, конкретный DI, номера веток, модель субагентов или фиксированную
матрицу ширин. Эти решения принадлежат проекту, а не KMP/CMP как технологиям.

## Применение в PhotoCombo

| Параметр | Значение / владелец |
|---|---|
| Активный модуль и target | `:composeApp`, `desktop`; `settings.gradle.kts`, `composeApp/build.gradle.kts` |
| Source sets | `commonMain`, `desktopMain`, `desktopTest`; Android-сборка legacy отдельная |
| Архитектура | README и инварианты AGENTS; `ArchitectureRulesTest` |
| Команды и отчёты | `docs/DEVELOPMENT.md` |
| UI-контракт | `docs/DESIGN_SYSTEM.md`; собственные низкоуровневые компоненты и PcIcons |
| Реальные примеры | `DesignSystemGallery`, `ComponentGalleryTest` |
| Продуктовая интеграция | Компоненты подключены к builder; остальные экраны мигрируют отдельно |

Пути в таблице — от корня репозитория. Они не являются зависимостями переносимых skills.

## Проверка набора

Для каждого skill выполнить `quick_validate.py` из доступного skill-creator:
это проверяет формат, не качество исполнения задачи. Проверить локальные ссылки,
достижимость из AGENTS и переносимость копированием только общего набора в пустой
каталог. Отдельно пройти сценарии с отличающимися target/toolkit/тестовыми хостами,
чтобы правила PhotoCombo не стали неявными универсальными требованиями.
